# Development Notification submissions

Run `npm run db:migrate`, then `npm run notifications:worker` from the repository root alongside the application. `npm run notifications:worker -- --once` processes at most one due submission and exits. The worker uses the same `data.db` as the application and reads Knock Development credentials from `.env` or environment variables through the server adapter. Production keys are rejected. Stop with Ctrl+C; committed processing claims recover after their lease expires.

Set `CADENCE_APP_ORIGIN` in `.env` or the environment to the Development application origin (for example `http://127.0.0.1:5173`). Links are captured when the domain action commits. Without an explicit origin the local development default is `http://localhost:5173`. Keep the worker and app in the same working directory. Email summaries contain actor/course/lesson context; full discussion content remains in Cadence. Hosted workflow provisioning and delivery evidence are separate from the network-free worker tests.

Domain services call `enqueueNotification(transaction, {eventKey, workflow, recipientId, actorId, data})` inside their existing synchronous Drizzle transaction. IDs are numeric Cadence person IDs; the adapter converts them to strings for Knock. Use a distinct durable event key for each committed domain transition, shared across its recipients. Repeating an event/recipient pair preserves its first payload and idempotency key. Self-targeted intents are excluded. `notificationData` builds the shared flat Feed/email fields and captures absolute links. Do not call the adapter inside this transaction.

`createDiscussionComment` is the common creation operation for the lesson and Instructor actions. Route actions retain their current authorization checks. It validates the parent and body, writes the comment, and queues an Instructor submission for a top-level Discussion Question atomically. Edits and deletions do not enqueue events. The historic seed intentionally starts with no submission obligations, so reseeding never submits old activity.

`processNextNotification(db, adapter, {now?, logError?})` is the worker boundary; `getNotificationSubmissions(db)` exposes persisted diagnostic outcomes. A synchronous immediate SQLite transaction claims one due row; the claim commits before identification or triggering. Concurrent processes sharing the same local SQLite file cannot claim an unexpired lease. Leases last 60 seconds, renew every 20 seconds during processing, and recover after restart. Claim tokens fence stale workers before triggering and before recording outcomes. Individual adapter operations time out after 30 seconds or the remaining budget, whichever is smaller. An outstanding timed-out vendor request may still complete, so retries retain the same immutable request and idempotency key.

Identification refreshes only the recipient's current name/email before every trigger attempt. It does not write preferences or roles. Both operations share a 23-hour budget starting at the first claim, regardless of event age. Retry delays double from one second to a one-hour cap and never schedule past the cutoff. At exactly 23 hours unresolved rows become retained `rejected` outcomes and produce an error log with the submission ID and sanitized reason. The worker checks cutoff before identification, before triggering and before recording acceptance; expired processing rows are also rejected by the next worker sweep. A stopped worker applies the cutoff on restart rather than replaying expired obligations. No automatic replay exists.

Accepted rows retain Knock's workflow-run ID and are never retriggered. Acceptance ends Cadence's submission responsibility; Knock owns downstream channel retries. Stable keys reduce duplicates but cannot guarantee exactly-once delivery. An ambiguously accepted workflow can continue even if Cadence ultimately rejects its local submission.
